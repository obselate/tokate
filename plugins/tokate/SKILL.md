# Tokate donor workflow

Help a donor take an approved issue to a verified draft PR. Tokate coordinates and verifies work. The donor's chosen harness codes. The owner controls policy, acceptance and merging.

Use CLI flags or the GUI. Bare `tokate` prints help. Confirmation asks once in a terminal unless `--yes` is set. With `--json`, `--non-interactive` or no terminal, confirmation gates preview without changes. Rejected consent uses `confirmation_required` naming `--yes`. Existing successful previews stay successful. Missing choices fail with `invalid_arguments` and name a flag. Use installed CLI help for command details. In the project checkout, `42` names issue 42 and its saved run. `42-1` names one of two active attempts. Elsewhere use `OWNER/REPO#42`. `tokate status` lists your unfinished saved work. Read the [donor guide](https://github.com/obselate/tokate/blob/main/docs/donors.md), [recovery guide](https://github.com/obselate/tokate/blob/main/docs/recovery.md), [public summary format](https://github.com/obselate/tokate/blob/main/AGENTS.md#write-public-pr-summaries) or [data boundaries](https://github.com/obselate/tokate/blob/main/docs/security.md) when relevant.

- Save choices with `tokate defaults set NAME --harness HARNESS --model MODEL --effort EFFORT`. Machine doctor explains installations with `--fix`, asks once in a terminal, applies with `--fix --yes` and accepts `--harness-path FILE`. Set a default with `--harness HARNESS --set-default`.
- Owner setup is `tokate init OWNER/REPO` with policy flags. It previews required Actions settings and a setup PR with only the policy and coordinator workflow, and asks once in a terminal. It writes no branch protection or access record. The workflow uses `obselate/tokate/.github/workflows/tokate-shared.yml@v0`. Use `--pin` for an exact release commit and `--yes` to apply without a question. The owner merges the setup PR. Verification commands and required checks are optional. Maintainer edits default to true with a policy opt-out. Approve existing issues with `tokate approve N [LOGIN] [--base-branch BRANCH] [--yes]`. Eligibility is `open` or `trusted`. Deny always wins. Create issues with `gh issue create` or the GUI.
- Honor consent for the task, harness/model/effort and time. Use `claim ISSUE NAME` or `work ISSUE NAME` for a profile, and `defaults check OWNER/REPO NAME` or `defaults check NAME` in a checkout. Terminal claim and work show the task, tool, model, effort and budget and ask once unless `--yes` is set. Repository work and stop ask once in a terminal or require `--yes` in non-terminal use. A profile supplies settings, not consent. Time flags need units, such as `--time 1h` and `--verify-time 20m`.
- Distinguish a managed harness launch from coding in this session. Loading the skill proves no adapter support or permission to launch another process. Declare external work and later editing tools accurately.
- Preserve saved work and inspect its state before repeating a write. If an issue has two active attempts, a bare issue number fails, writes nothing and lists the attempts. Pending grants no coding authority. Never bypass failure with another run. Retries, tool changes and budget extensions need consent.
- Keep authentication with the harness. Never inspect credential files, mixed settings or environment dumps for model discovery.
- Publish only when authorized. Report the actual contribution state and who must act next. A successful status read does not prove successful work.
